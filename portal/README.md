# חלק ג' — פורטל לקוח (Next.js על Vercel)

כל לקוח נכנס דרך קישור אישי, ורואה רק את ההזמנות שלו ואת השלב שבו נמצא כל פריט. הנתונים נשלפים חיים מ-monday. מאותו דף הלקוח שולח הזמנה חדשה, בטקסט או בקובץ, והיא נכנסת ל-monday כטיוטה ועוברת לסוכן של חלק ד'.

```
דפדפן הלקוח ──► Next.js על Vercel (שרת) ──► monday GraphQL API
   (רק HTML)       │  MONDAY_TOKEN בשרת בלבד
                   ├──► הסוכן ב-Render (חלק ד') — AGENT_URL/portal ו-AGENT_URL/ask. מפתח ה-AI נמצא אצל הסוכן
monday ── webhook ─┘  /api/webhooks/monday  ← מנקה cache, והשינוי מופיע מיד
```

## הרצה ופריסה

```bash
npm install
cp .env.example .env.local      # למלא MONDAY_TOKEN ו-MONDAY_WEBHOOK_SECRET
npm run dev                     # http://localhost:3000/c/<קישור>
npm test                        # בדיקות למיפוי ולהפרדה בין לקוחות

# פריסה
npx vercel                      # או push ל-GitHub וחיבור ל-Vercel
npx vercel env add MONDAY_TOKEN production
npx vercel env add MONDAY_WEBHOOK_SECRET production
```

**בדיקה מקומית בלי monday:** `node scripts/mock-monday.mjs`, ואז `MONDAY_API_URL=http://localhost:4010/v2 MONDAY_TOKEN=x npm run dev`. השרת המדומה מחזיר תשובות בצורה שהתקבלה מה-API האמיתי. הוא גם מכניס לרשימה בכוונה הזמנה של לקוח אחר, כדי לבדוק שהיא נחסמת.

## זיהוי הלקוח

### ב-MVP: קישור אישי

- **הקישור:** כל לקוח מקבל `/c/<token>`, באורך 32 תווים ו-192 ביט אקראיים. אי אפשר לנחש אותו.
- **מה נשמר ב-monday:** רק ה-SHA-256 של הקישור, בעמודה "מפתח פורטל (hash)" בלוח לקוחות. מי שרואה את הלוח לא יכול לשחזר ממנו קישור.
- **הנפקה וביטול:** `node scripts/portal-link.mjs <item id>` מנפיק קישור חדש, ומאותו רגע הקישור הישן לא עובד יותר.
- **הקישור לא דולף:** `Referrer-Policy: no-referrer` מונע ממנו לעבור לאתרים אחרים, ו-`noindex` מונע ממנו להופיע במנועי חיפוש.
- **אין רמזים מהשגיאות:** קישור לא תקין וקישור לא קיים מחזירים בדיוק את אותה הודעה, כך שאי אפשר לדעת אם קישור מסוים קיים.

**למה קישור ולא סיסמה:** הפורטל מיועד למנהלי עבודה באתר בנייה, מהטלפון. שם סיסמה פשוט לא תשמש. קישור בוואטסאפ זה הערוץ שהם כבר עובדים בו מול רינה.

### מה הייתי עושה בייצור

1. **קישור לכל איש קשר ולא לכל לקוח,** עם הרשאה לפי פרויקט. מנהל העבודה בחדרה יראה רק את חדרה.
2. **כניסה בקוד חד-פעמי** ב-SMS או וואטסאפ למספר של איש הקשר, שיוצר session ב-cookie מסוג `httpOnly`. ככה הקישור לבדו כבר לא מספיק.
3. **תפוגה וביטול אוטומטי** כשאיש קשר עוזב, ו-audit log של כניסות.
4. **הגבלת קצב משותפת** ב-Redis (למשל Upstash). היום היא בזיכרון של כל instance.
5. **תפקיד "בעלים" שרואה מחירים,** רק אם יוחלט כך. זו שאלה פתוחה 1 בחלק א'.

## אבטחה

| דרישה | איך זה ממומש |
| --- | --- |
| הטוקן של monday לא בדפדפן | רק ב-`lib/monday.ts`, שמתחיל ב-`import "server-only"`: ייבוא שלו מקוד צד-לקוח יכשיל את ה-build. אין משתנים עם `NEXT_PUBLIC_`. בדקתי ב-build שהכתובת `api.monday.com` מופיעה רק בקבצי השרת |
| מפתח ה-AI לא בדפדפן | הוא לא נמצא בפורטל בכלל. הפורטל מעביר את ההזמנה לסוכן, שרץ בשרת משלו, עם סוד משותף |
| לקוח רואה רק את שלו | הזיהוי מתבצע בשרת לפי ה-hash. הרשימה מגיעה מהחיבור בכרטיס הלקוח, **ובנוסף** כל הזמנה נבדקת שהיא מקושרת ללקוח הזה. הבדיקה הכפולה מכוסה בבדיקה אוטומטית |
| אין דליפת מחיר | השליפה מ-monday מבקשת רשימה סגורה של עמודות (`config.ts`). מחיר, חיוב, הערות פנימיות ו"לבדיקה" לא נשלפים בכלל |
| העלאת קבצים | עד 10MB, רק סוגים מותרים, הגבלת קצב, והזיהוי נעשה מחדש בשרת בכל בקשה |
| webhook | סוד בכתובת, נבדק בהשוואה שלא חושפת מידע דרך זמן התגובה (`timingSafeEqual`). webhook רגיל של monday לא חתום |

## הזמנה חדשה ← הסוכן

`POST /api/orders` מקבל טקסט, קובץ, או את שניהם:

1. **בונה טיוטה ב-monday:** סטטוס "טיוטה", ערוץ "פורטל", מחוברת ללקוח. הטקסט נשמר בהערות והקובץ בעמודה "קבצי מקור".
2. **מעביר לסוכן:** אם `AGENT_URL` מוגדר, שולח ל-`AGENT_URL/portal` `{orderItemId, clientId, clientName, text, fileName}` עם הכותרת `x-portal-secret`.
3. **לא תלוי בסוכן:** אם הסוכן לא זמין, הטיוטה כבר שמורה, והסוכן יכול לאסוף טיוטות פתוחות בעצמו. הלקוח לא מקבל שגיאה בגלל תקלה אצל הסוכן.

הלקוח רואה מיד את ההזמנה החדשה ברשימה, במצב "התקבלה, בבדיקה אצלנו". כשרינה מאשרת, היא הופכת לפריטים עם שלבים.

## בונוס: תיבת "איפה ההזמנה שלי?"

`/api/ask` מזהה את הלקוח לפי הקישור, מגביל קצב, ושולח לסוכן (`AGENT_URL/ask`) רק את מזהה הלקוח ואת השאלה. הפירוט בחלק ד'.

## בונוס: webhook מ-monday

הדף נשען על cache של 30 שניות כדי לא להעמיס על monday. ה-webhook מנקה את ה-cache ברגע שמשהו משתנה, ולכן השינוי מופיע מיד.

**יצירה** (פעם אחת, אחרי הפריסה), ב-API Playground של monday:

```graphql
mutation {
  a: create_webhook(board_id: 5108619492, event: change_column_value,
       url: "https://<domain>/api/webhooks/monday?secret=<MONDAY_WEBHOOK_SECRET>") { id }
  b: create_webhook(board_id: 5108619492, event: change_subitem_column_value,
       url: "https://<domain>/api/webhooks/monday?secret=<MONDAY_WEBHOOK_SECRET>") { id }
}
```

ה-route עונה ל-challenge ש-monday שולח כשיוצרים webhook.

**השלב הבא:** הודעה יזומה ללקוח, למשל וואטסאפ "הפריט מוכן לאיסוף" כשהשלב עובר ל"מוכן". צריך לשם ספק הודעות, ואין אחד בהיקף של המטלה.

## מה נבדק

- **מול monday האמיתי:** השאילתה שמוצאת לקוח לפי hash, שליפת ההזמנות והשורות, יצירת טיוטה, והעלאת קובץ ל-`/v2/file`.
- **מקומית מול השרת המדומה:** הדף, דחייה של קישור שגוי (404), דחייה של הזמנה ריקה ושל קובץ exe, הגבלת קצב (429), webhook בלי סוד (401), challenge, וחסימה של הזמנה של לקוח אחר.
- **`next build` ו-`tsc`:** עוברים, ו-5 בדיקות יחידה עוברות.
- **מובייל:** צילום מסך ברוחב 390px, עם RTL.
